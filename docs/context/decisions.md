# Decisions

Scope: why things are built the way they are — rationale, tradeoffs, rejected alternatives, known constraints. Not a bug tracker, and **not a changelog**: entries state the rule as it stands now, and a reversed decision is rewritten down to its surviving lesson rather than given an addendum. Entry shape (Now / Why / Rejected / Consequence) is defined once in [doc-maintenance.md](./doc-maintenance.md#decisionsmd-entry-shape).

## Politics → Power, Checkpoint → Impact rename
**Now:** both systems carry their production UI names across every wire field, config key and Redis-persisted field — not just docs and code identifiers. **Consequence:** deploy client and server together; a room in flight during that deploy will not restore its Impact/Power state from an old-shaped Redis snapshot.

## Removed systems (stale references you may still hit)
- **Power token economy** — gone. No power has a token count or per-level cap; activating a held item *is* the effect.
- **UI skin switching** — gone. **Rejected:** two swappable skins (`DefaultSkin`/`Figma_SkinV1`) with a runtime picker → every scene edit had to be made twice. [Game UI Scene](./ui.md#game-ui-scene) is the one gameplay UI; no `ProjectSettings` skin preference or picker group exists.
- **Docker EC2 staging** — the EC2-1/2/3 workflows, Terraform and Ansible are fully removed; the K3s lab (`infra/k3s`) is the active stack → [deployment.md](./deployment.md).
- **Client HTML5 Pages (GitHub Pages deploy)** — `Client-HTML5-Pages.yml`/`-Undeploy.yml` and the `play.tod.galaxxigames.com` custom domain are fully removed; the Godot client has no web-hosted deploy target today (Android via [Android Deploy wsplaytod](./build.md#android-deploy-wsplaytod-workflow) and the physical backup's `devtod1`/`devtod2` remain). **Rejected (kept as rework guard):** Cloudflare Pages → a 25 MiB per-file cap on every plan blocks a 35.95 MiB `index.wasm`; the cap applies to the stored file so compression doesn't help.
- **Exact-finish/overbuild score popup** — gone. The `exact_finish`/`overbuild_finish` `scoreEvents[]` types still arrive on the wire (`displayOnly`), but `ScorePopupController` drops them before building a popup; the Top Indicator ([ui.md](./ui.md#main-ui-controller)) already shows exact/overbuild state live, so the level-end callout was redundant.

## PointerTriggerRouter removed → native per-trigger signals
**Now:** each popover trigger wires its own native `.pressed` signal ([coding-conventions.md](./coding-conventions.md#client-gameui-module-family-pattern)). **Rejected:** a shared `_input()` hit-test router (`PointerTriggerRouter`) → it existed only because a popover's full-screen `OutsideCatcher` (a later sibling than the triggers) wins normal GUI hit-testing while a popover is open, and it never fixed the tap bug blamed on it.
**Landmine:** that bug was a same-tap self-close race in [Popover Panel](./ui.md#popover-panel) hitting every trigger equally, not Power-specific wiring — fixed by an `OUTSIDE_TAP_GRACE_MS` (250 ms) window on `OutsideCatcher`.

## Team Inventory popover removed → always-visible Team Inventory Panel
**Now:** a permanently-visible [Team Inventory Panel](./ui.md#team-inventory-panel) bar shows the shared draw pile, reusing the `DrawPilePreview`/`DrawPileNameLabel`/`DrawPileCountLabel` nodes verbatim so [InventoryController](./ui.md#main-ui-controller) needed no logic change; `QuickChatTrigger` took the vacated slot. **Rejected:** a centre-aligned row → the `VSeparator` between the labels crowded the panel's right edge as the count text grew; the row is left-aligned (`alignment = 0`).
**Landmine:** labels on a white card need an explicit dark `font_color` override — the shared `CardMetaLabel` theme variation defines none and falls through to a near-white default, invisible on `WhiteCardPanel`.

## Tower Stability must stay a pure function
**Now:** `Tower_Stability.js`'s `settleBlock()`/`evaluate()` are pure, deterministic functions of the `entries` array — no history, randomness or hidden state. **Why:** the [Balance Simulator](./testing.md#balance-simulator) re-runs `evaluate()` thousands of times and needs reproducible results, and the client re-derives the same tilt from a `game_state` snapshot after reconnecting rather than replaying placement history. **Consequence:** any change to this module must preserve determinism.

## Private Asset Pipeline credential split
**Now:** CI holds an **Object Read only** R2 token (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` secrets) and cannot publish or delete art; only local dev holds an **Object Read & Write** token (gitignored `.env.art`), so publishing (`art-push.sh`) is local and manual by design. **Why:** Cloudflare's R2 S3-compatible endpoint doesn't accept GitHub OIDC federation (unlike the AWS Terraform workflows, which do use OIDC), so this path needs static credentials and the read/write split is the mitigation.
**Consequence:** automating publish would need a write token in GitHub Secrets and defeat the split. The guarantee covers repo and history only — art *is* extractable from a shipped build (`.pck` extractors are commodity tooling; the HTML5 build serves the `.pck` as a public download). `Cor/Art/` is a build input, not a secret; encrypting the PCK wouldn't change that, since the key would ship inside the exported binary.

## Caddy gateway ACME cert cache persisted to R2
**Now:** the ACME cache round-trips through a dedicated R2 bucket around each deploy, plus a post-start liveness check that fails fast with `docker logs`. Mechanism → [deployment.md](./deployment.md#caddy-gateway-acme-cert-persistence-r2). **Why R2 over S3:** avoids widening AWS IAM scope and reuses existing free usage.
**Why:** EC2-GW's root volume is ephemeral, so each `terraform destroy`/recreate wiped Caddy's automatic-HTTPS state and forced a fresh Let's Encrypt request; repeated cycles within a week hit the **"5 duplicate certificates per identifier set per 168h"** limit and blocked the public WSS smoke test with `429 rateLimited` — surfacing only as a generic 5-minute timeout, since nothing checked whether Caddy actually stayed up.
**Landmine:** the archive carries the live ACME account key and TLS private key — both the runner and EC2-GW chmod it `0600` immediately and delete it once consumed.

## Physical backup: dev instances and demo, one shared tunnel
**Now:** the physical backup runs two dev game servers (`devwstod1`/`devwstod2`), two dev web servers (`devtod1`/`devtod2`), and one always-on public demo pair (`wstoddemo`/`toddemo`, instance 3 — bots on, debug UI off) behind one Cloudflare Tunnel, all one level below the zone apex. Script logic (`scripts/backup/`) is tracked in the repo; only credentials and per-run state (`.env.backup`, `web-content-*/`, the Tunnel's own config) stay in a machine-local `$CORP_TOWER_BACKUP_STATE_DIR`, kept out of the repo checkout because `actions/checkout`'s clean step wipes gitignored/untracked files inside it on every run.
**Why one level deep:** Cloudflare's free Universal SSL covers the zone apex and exactly one subdomain level, so a two-level name behind a *proxied* record (which a Tunnel requires) hits a bare TLS handshake failure — every K3s hostname escapes this only because it's DNS-only, with Caddy fetching its own cert. Reusing an existing two-level Pages hostname for a Tunnel doesn't dodge this either: cutting `play.tod.galaxxigames.com` to a Tunnel surfaced `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` even though a cert for that name already existed — Cloudflare's edge, not GitHub's, terminates TLS for a proxied record.
**Rejected:** keeping the up/down/status scripts entirely out-of-repo → the multi-instance fan-out needed review, CI, and history; only genuinely secret material (tokens, per-run state) still lives outside. Also rejected for the demo: an always-on cloud dev cluster, and reaching it through `Backup-Deploy-All.yml`'s push-triggered path — both cost more or risk a routine commit silently redeploying a link on a résumé.
**Consequence:** no Redis on the backup (single machine on `Redis_State.js`'s in-memory fallback — correct here, wrong for multi-replica K3s); game servers bind loopback only (`127.0.0.1`), matching the web servers — `cloudflared` is the only intended caller for both. `cloudflared` runs as a **user-level** systemd service since a self-hosted runner has no TTY for a `sudo` password prompt; `loginctl enable-linger` is required once so it survives non-interactive sessions. `stop_cloudflared_if_idle` (`backup-common.sh`) only stops the tunnel once **all six** containers are down — with the demo always running, the tunnel now effectively never stops on its own.

## Auto-deploy guard rails check live status, not a stored flag
**Now:** `Backup-Deploy-All.yml` auto-deploys on push (game and/or web, per which paths actually changed) behind a job probing the target's actual live state: `docker ps` for `corp-tower-server-1`/`corp-tower-web-1` specifically, on the self-hosted `backup` runner. Push events always target `devwstod1`/`devtod1` — `devwstod2`/`devtod2` (and `all`) are manual-dispatch-only choices on the same workflow.
**Why:** unguarded, an auto-deploy silently undoes an intentional stand-down on the next matching push. **Rejected:** a stored flag a separate workflow must remember to set → a runtime check can't drift out of sync.
**Landmine:** the backup guards are self-hosted jobs — they **queue indefinitely with no timeout** when the physical machine's runner is offline, so a push while the machine is off just waits rather than failing fast.
**Consequence:** each guard inspects only its own target's live state, so all four backup instances stay fully independent — and it gates the `push` trigger only, so manual `workflow_dispatch` always runs regardless of live state.

## A skipped guard job cascades to skip downstream jobs unless their `if` says otherwise
**Landmine:** a job's default `if` is `success()`, which evaluates against its **entire upstream dependency graph**, not just its direct `needs` — so a job downstream of a conditionally-skipped guard job silently skips too, even when its own direct dependency succeeded. Give every job placed downstream of a conditionally-skipped job an explicit `if: always() && needs.<dep>.result == 'success'`.

## Nested reusable workflows can't detect their own trigger via event name
**Now:** kept for the gotcha alone — the `workflow_call` triggers and `invoked_via_call` inputs are gone along with `Client-HTML5-Set-Live-Host.yml`, so the confirmation guards run unconditionally, gated only by their `workflow_dispatch` confirmation string.
**Landmine:** `github.event_name` reflects the *top-level* run's trigger event, unchanged however many `workflow_call` levels deep a job sits — so `if: github.event_name == 'workflow_dispatch'` fired each confirmation gate (`CLEANUP_WEB_BACKUP`, `UNDEPLOY`) on the fully-automated path too, and the first real test of automatic failover failed before ever reaching the backup machine. The shape that works is an explicit boolean declared only under `on.workflow_call.inputs` and checked as `inputs.invoked_via_call != true`, since `inputs.*` genuinely is scoped per-invocation.

## DNS cutover verification must use the Cloudflare API, not `dig`, for proxied records
**Now:** `scripts/backup/backup-common.sh`'s `wait_for_cname` (shared by all four instances' up-scripts) re-queries the Cloudflare API (`dns_records?type=CNAME&name=...`) and compares `.result[0].content`; `dig` is out of these scripts' `require_cmd` lists entirely, and `backup-server-status.sh`/`backup-web-status.sh` read DNS the same way so operator output can't show a healthy record as blank.
**Rejected:** polling `dig +short $name CNAME` after an upsert → Cloudflare **never exposes a literal CNAME to public resolvers for a proxied (orange-cloud) record**, resolving the hostname straight to its own anycast A/AAAA addresses instead, so the query is always empty and the wait loop always timed out and `die`d.
**Consequence:** the API reflects a write immediately, so the retry loop is a small safety margin against a transient read, not a propagation wait.

## EKS kept session-scoped, not always-on
**Now:** `infra/eks` Terraform is fully implemented and apply-ready (`EKS-Infra-Apply`/`EKS-Infra-Destroy`/nightly `EKS-Infra-Auto-Destroy` exist) — the production-grade target, brought up for a session (hours) and torn down after rather than left running continuously. First apply also needs one-time manual setup: an expanded `AWS_ROLE_ARN` IAM grant (CI cannot grant itself permissions), the persistent `infra/eks/terraform-shared` ACM/Cloudflare root, an operator IAM ARN for cluster-admin access, and AWS Budgets alerts.
**Why:** the control plane, NAT Gateway, ALB, and ElastiCache have no free tier — every hour of existence spends real credits, so an always-on or auto-applying stack is an uncontrolled cost lever the nightly auto-destroy is built to prevent.
**Rejected:** an AWS Load Balancer Controller + IRSA + `TargetGroupBinding` for target registration → adds a Helm install and IRSA wiring this stack doesn't need; `target_type=instance` NodePorts registered via `aws_autoscaling_attachment` reuse the same NodePort numbers K3s already standardizes on, with zero extra controllers.
**Consequence:** every session pays ~15min apply / ~14min destroy in AWS-side latency (control plane + node group create/delete) that no workflow change can shorten.

## EKS node security group must carry its own control-plane and self-referencing rules
**Now:** the node launch template sets `vpc_security_group_ids` to a single custom `nodes` SG (`infra/eks/terraform/security_group.tf`), so three ingress rules exist explicitly: node→control-plane (443) and control-plane→node (1025-65535) against `aws_eks_cluster.main.vpc_config[0].cluster_security_group_id`, plus a self-referencing all-traffic rule on `nodes` itself.
**Why:** specifying any custom SG on the launch template replaces, not extends, EKS's default automatic node↔control-plane and node↔node SG wiring — opting out is silent, with no error at apply time.
**Rejected:** relying on the default reciprocal trust → node group creation hangs then fails with no diagnostic pointing at the SG; the self-referencing rule specifically is easy to miss because its absence still lets the cluster come up — it only drops cross-node pod traffic (CoreDNS replicas, cross-node service routing), surfacing as intermittent `getaddrinfo EAI_AGAIN`/connection-timeout on whichever pod's DNS query lands on the other node.
**Consequence:** any future custom node SG (new node group, different launch template) must re-add all three rules; there's no way to inherit them.

## EKS Infra Destroy verifies orphans against live EC2, not the tagging API alone
**Now:** the post-destroy orphan check (`EKS-Infra-Destroy.yml`) cross-verifies every ARN the Resource Groups Tagging API still lists against a direct `describe-*` call for that resource type before failing the run.
**Why:** the tagging API is a separate, eventually-consistent search index that can keep listing a resource's ARN for minutes after the resource is actually deleted — worse for NAT Gateways, which linger in a `deleting` state before fully gone.
**Rejected:** a bare retry loop against the tagging API alone → observed lag outlasted a 2.5-minute/5-attempt retry window with the same stale ARNs on every attempt, so it was never going to clear on its own.
**Consequence:** any future orphan-resource check needs the same live cross-verification, or it will false-fail a clean destroy.

## EKS deploy workflows fail fast on infra code the last Infra Apply never ran
**Now:** `EKS-Infra-Apply` records the applied `infra/eks/terraform` git tree hash to `eks-lab/applied-infra-tree.txt` in the state bucket; both EKS deploy cores run a `verify-infra` job (`.github/actions/eks-infra-drift-check`) that hard-fails before any build job on a tree mismatch, and warns without failing when no marker exists.
**Why:** deploy workflows run no Terraform, so a committed-and-pushed infra fix is inert until an Infra Apply runs on that commit — nothing else surfaces the gap.
**Rejected:** trusting "the fix is on `main`" → the nodes-SG self-referencing rule sat committed but unapplied while repeated `EKS Deploy All` runs failed on the exact symptom it fixes.
**Consequence:** any change under `infra/eks/terraform` needs an `EKS Infra Apply` before the next deploy passes; deleting the S3 marker downgrades the guard to a warning, not a pass.

## Argo CD prepared but not enabled
**Now:** bootstrap manifests exist (`infra/k3s/argocd/bootstrap`), covering both `corp-tower-prod`/`corp-tower-test`; nothing installs or applies them. **Why:** enablement waits on install → one manual sync → a passing rollback test, and only then automated prune/self-heal; `GITHUB_TOKEN` is not a suitable long-lived Argo CD repo credential for private repos — a persistent repo-read credential is needed instead.

## Debug menu build flag
**Now:** `EndpointConfig.DEBUG_UI_ENABLED`, written by `scripts/write-endpoint-config.sh` per build, gates the debug button's visibility (`ScreenManager._ready()`). Off for the two K3s web builds (`playtod`/`todtest`); on for Android, the editor, and the physical backup's dev builds.

**Consequence:** still UI-only — client JS is inspectable, and server-side `update_config`/`resetDebugConfig` still have no admin/auth check beyond existing message validation. Full gating needs server-side authorization too, before public release.

## Debug menu category navigation switched from tabs to a dropdown
**Now:** a plain `Control` holds the category `ScrollContainer`s stacked full-rect, with a `DebugCategoryDropdown` `OptionButton` toggling `.visible` on exactly one at a time — every category's rows and their `configure_slider()`/`apply_config()` wiring untouched. **Rejected:** the `TabContainer` header row, and shrinking or wrapping its labels → visibly cramped at 8 categories, where a dropdown scales to arbitrarily many with zero added header space; categories were expected to keep growing, and have (10 now).

## Debug Tooltip: a purpose-built dimmed popup, not a reuse of Popover Panel
**Now:** `DebugTooltip.gd` mirrors [Popover Panel](./ui.md#popover-panel)'s outside-tap/grace-period shape (`OUTSIDE_TAP_GRACE_MS`) but adds a semi-transparent `ColorRect` dim layer, keeping the two components' behavior contracts independent. **Why:** debug rows' calibration variables (`scroll_start_ratio`, `scroll_ease_power`, …) aren't self-explanatory from a slider, and a modal explainer over an already-modal debug panel reads correctly dimmed — while the Chat/Power/Quest popovers are anchored corner cards over live game content, where dimming would be wrong.
**Rejected:** adding a dim option to the shared `PopoverPanel.gd`/`.tscn` → risks behavior changes to the three existing popovers.

## No persistent leaderboard yet
**Now:** Redis holds active-session state (matchmaking/reconnect/room snapshots) only; durable leaderboard/player-stat storage and structured logging are future technical work. **Also untested at integration level:** reconnect and gateway routing across pods, beyond the matchmaking queue regression tests ([testing.md](./testing.md#server-matchmaking-queue-tests)).

## Matchmaking queue lost-update and cross-pod room gaps
Three independent multi-pod gaps in the same mechanism — two players joining from the same network at nearly the same moment (plus a third from elsewhere) could end up unable to reach or act in the room, depending on which pod formed it and which pod holds each socket. Identity is `playerId`/`reconnectToken`-based, never IP-based, so the cause was never there. Coverage (items 1–2) → [testing.md](./testing.md#server-matchmaking-queue-tests).
1. **Lost-update race in the shared queue.** **Now:** `dequeueRealPlayers(maxCount)` (atomic `RPOP ... count`) plus `requeuePlayers(players)` (atomic `RPUSH` of only what was taken back out), neither of which can clobber an entry it never touched. **Rejected:** `replaceQueue()`'s read-all/rewrite-all (`DEL` + rewrite) → `addPlayer()` calls the unlocked `enqueuePlayer()` *before* taking the matchmaking lock, so another pod's entry landing in the read/write gap was silently wiped and that player stayed connected but queued nowhere. Deleted outright rather than kept as a fallback, since the gap *was* the defect.
2. **Cross-pod delivery gap.** **Now:** a lightweight `player:assignments` pub/sub event (`publishPlayerAssignment`/`subscribeToPlayerAssignments`) whenever a room-assigned player isn't locally connected; the pod owning that socket calls `resumePlayer()` through the existing `hydrateRoom()`/room-channel-subscribe path. **Why:** the pod winning the matchmaking lock runs `createRoom()` but holds live sockets only for its own players, so with 2 replicas behind round-robin a teammate on another pod was added to the room server-side while `sendPlayer()` silently no-op'd on a `null` `ws` and `room_created` never arrived. **Rejected:** a parallel state-relay mechanism → the genuine-reconnect path already does exactly this.
3. **Post-handoff action gap.** **Now:** `place_block`/`send_quick_chat`/`activate_power` go through `LobbyManager.dispatchRoomAction()` — run locally only when `isRoomOwner(room)`, else republished on `room:<id>:actions` (`publishRoomAction`/`subscribeToRoomActions`) for the owning pod to execute. **Why:** a handed-off player's local `engine.room` is a one-time `hydrateRoom()` snapshot, never refreshed by later broadcasts (`subscribeRoom` relays messages straight to sockets, not back into local room state) — and it's hydrated within a Redis round-trip of room creation, almost always still `"starting"` well before the 1s `startDelayMs` transition — so calling the engine directly on that pod failed its `state !== "playing"` check forever, silently. **Rejected:** re-hydrating the local snapshot on every relayed broadcast → still leaves two independently-mutable copies of one room; the owning pod must stay the sole writer.

## Fixed brick size + parallax scroll replaces shrink-to-fit tower rendering
**Now:** bricks stay `brick_unit_size` (34px) **always** and the view pans up like a camera — HUD fixed, tower and background moving. No scroll at all while `target_height` already fits under the Top Indicator; above that, none below `scroll_start_ratio` of visible capacity, then a `pow(progress, scroll_ease_power)` ease from the start row toward the flush row as `current_height` approaches `target_height`, frozen once target is reached so overbuild bricks ride up and tuck *under* the indicator. The scroll/tilt/drop values are `@export var`s so the Debug Overlay's Parallax category can tune them live, client-side with no server round-trip. **Exception — the Impact Beat** ([ui.md](./ui.md#leaf-components)): for ~2s at level end the camera zooms out so the whole tower is visible while every brick flips to its placer's Impact verdict, then zooms back in. The zoom is derived per level — `clamp((available_height / brick_unit_size) / (max(current, target) + clearance), impactBeatMinZoom, 1.0)` — so `impactBeatMinZoom` (0.3) is a **floor, not the zoom**: a level whose tower already fits yields `1.0` and simply plays the wave with no camera move, and the whole thing self-corrects if the target-height curve moves. One knob, not two: `_scroll_offset_units()`/`_visible_unit_capacity()` already take the zoomed unit, so a smaller brick grows the visible capacity and the scroll ramp resolves toward 0 by itself. Its two toggles round-trip through the server (whole room), like the brick-face mood threshold and unlike the client-local Parallax rows, because the durations already live in `Game_Config` and all three players must see the same beat.
**Rejected:** shrinking bricks to fit → bricks rendered visibly smaller than designed on tall towers. **Rejected:** a `Camera2D`/viewport-follow redesign → the client is entirely `Control`-node based with `TowerStack` drawing bricks via raw `_draw()`, not `Node2D` children a camera can pan; it means re-architecting `TowerStack`/`BlockPreview`/`BackgroundParallax` and the drag hit-testing math for a bug fixable as a scalar/timing correction. **Rejected:** ordering `TopIndicatorRow` before `TowerStack` in `GameUI.tscn` → the tower drew over the bar; the current node order is deliberate. **Rejected:** a pan-down-only Impact Beat (ease scroll to 0, no zoom) → a 40-row tower still shows only its top 16 rows, so the reveal is partial and the "look at what you built" moment doesn't land. **Rejected:** a scroll-bias/override term alongside the beat's zoom → redundant, since every scroll term already reads the zoomed unit.
**Landmine — a constant ratio cannot cancel an easing-induced lag.** `PlatformArt` at `parallax_ratio = 1.1`, against `BackgroundParallax` easing via `lerpf` while `TowerStack`'s scroll applies instantly, left a residual gap of `−7 + 0.1 × scroll_pixels`: fine at low scroll, unbounded past ~70px. The fix is `parallax_ratio = 1.0` plus a per-instance `instant` flag that snaps `PlatformArt` in the same frame as the brick redraw. `BgArt` keeps eased motion (no ground-contact requirement).
**Landmine — the platform is background, not HUD.** It recedes with the parallax, so `_is_rect_visible()`'s bottom bound extends to the real screen bottom and old bricks are hidden by later-drawn siblings; clipping at the Control's own rect while the ground sank past it made the tower appear to float. The beat's zoom has the same failure mode on the other axis: `Main.apply_camera_zoom()` must pivot `PlatformArt` on its top centre before scaling, or the ground shrinks away from the bricks resting on it. **Camera follow during a collapse is deliberately out of scope**, and the cost is known: on a scrolled level the debris pile lands below the viewport, so `CollapseSim` is invisible on most failures.
**The revealed sky is a placeholder** — the existing solid-colour `Background` panel stands in behind `BgArt`. A flat colour has no edge so it pans any distance; a real replacement must be **seamlessly vertically-tileable** to keep that property, not merely a taller image.

## Two-axis stability: Lean + Integrity replaces the single tilt scalar
**Now:** `stability = min(leanStability, integrity)`. **Lean** keeps the three asymmetry terms and still drives `tiltAngleDeg`, so `TowerStack`'s tilt rendering needed no change; **Integrity** adds slenderness (site width ÷ ground width — see [the stability dial](#tower-stability-is-one-derived-dial-scaled-by-level)) plus a whole-tower support deficit. The existing 0–100 scalar, the warning/critical thresholds and the client readout all keep working unchanged.
**Why:** every Lean term measures *asymmetry*, normalised by the tower's **own** ground footprint, and none measures slenderness — a centred 2-wide, 40-tall O-spire measured `stability 100, tiltScore 0.000`. The height-optimal play (build a spire) was also the stability-optimal play, so stability constrained nobody and the [Balance Simulator](./testing.md#balance-simulator)'s greedy bot "building narrow towers" was correct play rather than a bot flaw. **Rejected:** reweighting the existing terms → no weighting of asymmetry measures slenderness.
**Consequence:** Integrity is recomputed from `entries` on every call, never accumulated — that is what lets a persistent-*feeling* score stay a [pure function](#tower-stability-must-stay-a-pure-function), and why adding well-supported bricks raises it, which is what makes repair a payable action.
**Landmine — small towers make every ratio degenerate.** With 4 cells placed a lone `T` resting on its stem is 50% unsupported and an `L`/`Z` leans ~10° immediately; both are the *intended* stability hook at scale, so the fix is a single maturity ramp (`min(1, height / towerStabilityMinHeight)`) applied to **all** penalty terms, not per-shape special cases. `towerBaseHalfWidthFloor` is **not** part of that fix — it is a divide-by-zero guard only, and using it as a difficulty lever is what killed the lean axis.

## Tower stability is one derived dial, scaled by level
**Now:** `towerStabilityDifficulty` (0–100) is the only stability tunable. A `pressure` scalar — difficulty × a level ramp — interpolates all seven physics constants between a forgiving and a harsh anchor set, so threat is near-absent at level 1 and real past level ~25 from a single number.
**Why:** nine raw constants in unrelated units were untunable in practice, and three could not reach their thresholds at all: `towerBaseHalfWidthFloor` above the site's real half-width pinned lean's divisor so `tiltScore` never passed 0.76 against a threshold of 6.0, and `groundWidth` being an integer 1–8 made the slenderness band a step function — 100 for anything reasonable, 0 for anything degenerate. **Rejected:** keeping the raw knobs and hand-tuning them → the units are the problem, and a per-level site cap means no absolute height÷width threshold both fires late and spares a perfectly played tall level.
**Consequence:** slenderness is measured as **site usage** (`siteWidth / groundWidth`), so a full-width base is free at every level and *only* the level ramp scales difficulty. Widening the site therefore widens the safe zone — the site knobs and the stability dial are coupled.
**Landmine — site usage is worst at the very first brick.** One narrow brick alone on the ground is maximal `siteWidth / groundWidth`; at high pressure this collapsed 47% of runs on placement one until the harsh `towerStabilityMinHeight` anchor was raised. Any future harshening must re-check the opening brick, not just steady-state play.
**Landmine — bot collapse rate cannot calibrate this.** `chooseBotPlacement` skips collapsing placements, so simulated collapse reads ~0% across wildly different configs; tune against `avgStability` and per-placement spread from the [stability sweep](./testing.md#balance-simulator).

## Brick faces read a lean-only balance delta, not the stability score
**Now:** each placed brick wears a fixed face from `balanceDelta` (lean-only, [formula](./backend.md#tower-stability)); the client compares it to the live `towerStabilityMoodThreshold` at draw time, so moving the knob restyles the whole standing tower instead of only later bricks.
**Why:** the change in `towerStability` cannot express placement quality. It is `min(leanStability, integrity)`, so a lean correction is invisible whenever integrity is the lower axis — which it was in nearly every sampled placement — and it sags on its own as the maturity ramp scales in, so a perfectly centred brick measured **−3 at level 1, −6 at level 8, −15 at level 20** with lean flat at `0.00`. `structuralLean` is read before that ramp, which is what removes the drift.
**Rejected:** subtracting the placed brick's `overhangPenalty` → over half of all placements carry some overhang (mean cost 11.8 points), so it re-created the same one-sided frown bias, and it double-counts: a dangling brick puts its mass off-centre, so `comOffset` already charges for it.
**Consequence:** the face grades *balance only*. A brick that is well-placed for balance but slenderness-fatal still smiles, and the two must not be reconciled by folding integrity back in.
**Landmine — never classify server-side and store the verdict.** Stamping a mood string froze it at placement, so the knob provably could not change a standing tower and read as dead. Store the number, classify in the view. A brick with no `balanceDelta` deliberately draws **no face**, since a neutral face is indistinguishable from a real "barely moved" verdict and hides a stale server.

## Supply was sized for vertical stacking, and made high levels unwinnable
**Now:** supply is sized against `ceil(targetHeight / packingEfficiency)`, with efficiency **derived** from brick geometry (`cells per brick ÷ (avg brick height × effective width)`) rather than fitted — measured 0.68 / 0.48 / 0.42 at site widths 4 / 6 / 8, which fits "you need one brick-layer across roughly half the site per height unit". The same reasoning replaced the 33-entry `generatedDrawPileScaling` table with a derived reserve count, so both self-correct if `brickWeights` or the site width change. That requirement is then trimmed by `levelSupplyPowerReserveShare` (**0.10**): the pile covers 90% of a level and a Replenish (25% of the starting pile, one per level from the side quest) insures the rest, so most levels finish unaided. Sizing instead to the bots' ~0.9 measured efficiency would starve a human — that figure is a spire-building artifact of ranking by height gain, and playing wide (which Integrity demands) lands near 0.4–0.6. `maxGeneratedDrawPileBlocks` is therefore a sanity ceiling against a bad config, **not a balance knob**: target height is uncapped, so a value that binds starves the level outright.
**Why:** accepting a level on `Σ brick.height ∈ [target, target + 6]` assumes one unit of brick height converts to one unit of *tower* height — true only for a single-column stack, while stability demands horizontal spread; measured completion collapsed from 88.5% at level 5 to **0% from level 12 onward**, every brick placed and target never reached. **Rejected:** applying the efficiency factor to `checkFailCondition` too → a test caught it failing a level while a winning move still existed (one height-3 brick genuinely *can* add 3 height if stacked). That check tests *impossibility*, so it needs the true optimistic upper bound.

## Buildable site width scales with target height
**Now:** the placeable site is derived from the level's target height (`evenRoundUp(target / towerSiteSlendernessTarget)`, clamped) and forced even so it stays centred; `getSiteWidthForHeight` re-evens after clamping so a debug-set odd bound can't push it off-centre. **Why:** fixed columns 4–9 stood a target of 40 on the same 6-wide base as a target of 3 — physically absurd, and the main reason tall levels were unreachable. Deriving beat a second hand-authored table, and one knob now reshapes the game's whole aspect ratio.
**Landmine — the ceiling is a viewport fact, not a design preference.** `TowerStack` is 272px wide at a fixed 34px brick, so only 8 grid columns are ever on screen; a site scaled to 12 silently culled bricks in columns the player could never see. `towerSiteWidthMax` is capped at 8 in config *and* in the debug clamp, and widening it means widening the tower viewport or shrinking bricks — [fixed brick size](#fixed-brick-size--parallax-scroll-replaces-shrink-to-fit-tower-rendering) is itself a deliberate decision.
**Consequence:** slenderness is measured as **site usage** ([the stability dial](#tower-stability-is-one-derived-dial-scaled-by-level)), so the site-width curve and the stability-pressure curve are coupled by design — `towerSiteSlendernessTarget` is tuned so the site reaches `towerSiteWidthMax` around the level where `towerStabilityPressure.fullPressureLevel` reaches full pressure, not independently of it.

## The client must derive its grid from the server, never hardcode it
**Now:** `towerGridWidth` and the resolved `placeableColumnMin`/`Max` are broadcast in `game_state` and held as `static var`s on `SnapGrid`, with the render centre *derived* as `(grid_width − 1) / 2`. **Why:** `SnapGrid` held them as `const`s (14 / 6.5) aliased into `TowerStack`'s own `const`s, so retuning `Game_Config.towerGridWidth` to 8 had the server sending columns 0–7 while the client still centred on 6.5 — drawing the entire tower 102px off-screen left, with no error anywhere.
**Rejected:** threading the values through ~8 static functions → far more churn for a value that is genuinely global for a whole level. **Consequence:** tests must call `reset_placeable_range()` between cases, which `test_snap_grid.gd` does.

## Scoring carries the selfish-cooperation tension
**Now:** placement score is multiplied by the stability the placer **inherited** (`placementStabilityFloor + (1−floor) × stabilityBefore/100`), and a **Reinforce** event pays for integrity gained, lean corrected, and cells put back on solid ground. Using stability *before* the placement is what makes "fix it, then claim" the rational order; paying on the result would reward a player for their own overhang. The two earners are priced **against each other**, not independently: `reinforceScoreCapShare` holds one repair to a share of an average height claim (`avgBrickHeight × placementScorePerHeight × level`), so repair is worth choosing on a hurt tower, can never be farmed, and re-prices itself when the brick mix is retuned.
**Why:** paying only for height gained meant widening the base or correcting a lean earned nothing, and collapse was a flat team-wide loss with no individual stake — the game's defining tension had no mechanical surface, and no config value could create one.
**Rejected:** a purely contested finite height pool → sharpens selfishness but still leaves stability an unrewarded shared punishment. **Rejected:** a personal collapse stake → needs per-player blame attribution the pure stability function can't produce, and reads as punitive.

## Impact every level, and the share is bounded by arithmetic
**Now:** `impactInterval` is 1, so filling the Impact bar *is* the per-level objective — viable only because rollback correspondingly replays the level just played instead of discarding up to three. `impactMinContributionShare` is **30%**, leaving a 70% contested margin. Power and the side quest also unlock at level 1, and Replenish is **quest-only** via two default-off flags (`powerGuaranteedBaseline`, `powerImpactMvpReward`) rather than deleted grant paths — under this interval the Impact-MVP path would hand one out *every* level.
**Why:** three players × the share is the fraction of a level's score pool that must split near-evenly; at 30% that is 90%, measured as unreachable by natural distributions — the current default sits exactly at that ceiling, so watch gate-pass-rate for regressions.
**Landmine:** the first measured gate pass rate was 0–8% and read as a fatal design flaw. It was a **simulator artifact** — the simulator let one bot place unboundedly in a row (128 while others scored 0) because it never modelled the per-player placement cooldown that forces a real room to interleave; with the cooldown modelled the true rate is 62–90%. Never trust a tuning number from a simulator that omits a real constraint.

## Bot strategies differ by risk appetite, not competence
**Now:** both bots pursue height — greedy takes the best height gain among any non-collapsing column, cooperative only among columns within `debugBotStabilityTolerance` of the *best available* stability. **Rejected:** having cooperative maximise stability outright → it spread bricks pointlessly, starved itself of supply and **lost to greedy on completion**: incompetence dressed as caution.
**Why the gate is relative rather than an absolute threshold:** an absolute one stops discriminating entirely once stability is tuned forgiving enough that every column reads healthy — which is exactly the live tuning state.
**Now:** cooperative additionally **yields its whole turn** (`{ type: "wait" }`) once it has banked its own Impact share while a teammate is short, since under a per-level gate that shortfall fails everyone; a bot that is short can never take that branch, so a room can't deadlock. **Landmine:** `getImpactScoreStatus` reads banked `score`, which only absorbs `levelScore` at level end — mid-level every player reads as short and the yield never fires without the same live-score correction the client's Impact bar applies.
**Consequence:** divergence is contingent on stability being able to punish. With collapse effectively impossible greedy wins both completion and gate (96% vs 88% at level 10); with stability biting, cooperative wins decisively (87% gate / 2% collapse vs 64% / 28%). Both are correct — with no risk there is nothing to be risk-averse about.

## Inactive powers stay defined behind the powerCatalog active flag
**Now:** each `powerCatalog` entry carries an `active: boolean` and `awardImpactPower()` filters to `active: true` before picking; only **Replenish** is active, so Refresh, Score Cap and Copy Score are fully defined but never granted and never surface in a player's Power list. Re-enabling any is a one-line flip in `Game_Config.js`. **Why:** a power-system redesign is in progress; the inactive three are reachable only through the Impact-MVP path, which picks randomly across the catalog (the baseline and side-quest paths are hardcoded to `"replenish"`). Replenish is the one that survived because supply, not hand quality, is what actually strands a team — it is also the power `anyPlayerCanRescueSupply()` checks before failing a level for insufficient height.
**Rejected:** deleting the inactive entries and their `activatePower()` effect branches → they would need re-authoring from scratch once new power designs are ready. See [gameplay.md](./gameplay.md#activation-and-effects) and [backend.md](./backend.md#game-config).

## Placement design lineage (superseded)
The current mechanic is [point-based snap resolution](#point-based-snap-resolution-and-the-docked-landing-ghost) on the per-level site from [Buildable site width](#buildable-site-width-scales-with-target-height). Still load-bearing from the four dead designs below: random rotation at generation (`Block_Supply.getRotations`), and the integer `column` wire field that replaced `lane`.

| Design | Why it died |
|---|---|
| **Size-1..6 block ladder** | Replaced by 5 fixed 4-cell bricks (`I`/`O`/`L`/`T`/`Z`) from level 1. Difficulty should come from height, timer, stability and site — not unlock gating. |
| **3 lanes (L/C/R) on a 5- then 9-wide grid** | Wide bricks anchored near a lane edge spilled into "overflow" columns: a silent hard-clamp bug where the right lane collapsed onto the centre lane's placement. |
| **Per-instance random `anchorX`** | Only bridged a 3-way discrete lane choice to a per-shape reference point; once placement became continuous the bridge was unnecessary. Also rejected: a contextual per-lane anchor (collapsed most brick widths onto identical placements) and wider lane spacing (lanes must stay adjacent). |
| **Fixed 14-column grid, columns 4–9 placeable** | The numbers are dead — grid width is a config value the client reads off the wire, and the site is derived per level. The *rule* stands: a brick's entire footprint must fit up front, which removed the overflow bug class. |

**Landmine:** that redesign's explicit non-goal — "no stability/balance rebalancing" — left a narrowed placeable footprint sitting under untouched stability weights and a target curve sized for the old geometry, and is the direct ancestor of both [Two-axis stability](#two-axis-stability-lean--integrity-replaces-the-single-tilt-scalar) and [Supply was sized for vertical stacking](#supply-was-sized-for-vertical-stacking-and-made-high-levels-unwinnable). Deferring a rebalance across a geometry change turned two tractable tuning problems into two unwinnable-game bugs.

## Point-based snap resolution and the docked landing ghost
**Now:** resolution is a **2-D pairing** in the node-free `SnapGrid` service — for every outline vertex of the dragged brick × every snap point on the platform and on every placed brick, the candidate origin is `point − vertex`; candidates outside the site or overlapping a placed cell are rejected and the smallest squared lattice distance wins. That pairing fixes the **release row, not the resting row**: gravity then runs from it, so a gap inside the tower is reachable while a brick aimed at nothing still falls. Beyond `snap_radius_units` it falls back to nearest-column aiming released above the tower, so a drag over open sky never dead-ends, and `origin_y` rides the wire only for a resolved aim. The pairing itself survives the fall as `aim_point`/`aim_origin_y`: the docked ghost renders there, not at the settled `origin_y`, so a legal target with nothing under it (an overhang, a void) still visibly docks instead of showing no ghost near the cursor at all — a bare settled-only ghost read as "this spot isn't placeable" to a player aiming under an overhang. The highlighted snap dot stays on the *post-fall* contact (`contact_pair`) rather than the aim, since the ghost's own position already shows the aim and marking it twice would be redundant.
**Why:** the prior mechanic was *named* corner-snap but resolved placement in pure 1-D column math (cursor x → fractional column, compared against candidate origin edges), ignoring the y axis and the placed tower's geometry — the drawn snap dots and the resolver were computed independently, so the dots were decoration. Releasing at the aimed row is what makes support deficit repairable at its source rather than only by dilution.
**Rejected:** *placing* at the snapped point with support checked as a legality rule (corner contact allowed, stability charging for the rest) → bricks hung in mid-air off a single diagonal corner, which reads as broken physics no scoring term can excuse; gravity from the release row gets gap-filling without it, and mis-aiming costs the placement instead of being blocked. **Rejected:** filtering to only "supportable" snap points → far fewer legal targets for the same outcome gravity produces for free.
**Consequence:** `place_block` carries an optional `originY`, so wire, both settle mirrors and the ghost preview move together — a server that ignores it silently reverts every client to top-of-tower placement.
**Landmine:** `SnapGrid.settle_origin_y`/`is_placement_legal` are line-for-line mirrors of `Tower_Stability.settleBlock`/`isPlacementLegal` — **any change to either server function must be mirrored or the preview silently lies** (all four sites carry a comment saying so); and `Number(null)` is `0`, so an absent `originY` must be tested *before* the numeric coercion, or every bot placement reads as "aim at row 0" and threads into the lowest gap that fits.
**Landmine:** `clear_snap_preview()` must stay separate from `end_snap_drag()` — merged, they wipe the drag state on the first move, since the pointer legitimately leaves and re-enters the drop zone many times per drag. Found by rendering the play field to PNG, not by unit tests: the snap math was correct in isolation the whole time. Placement visuals still need eyes on a real build.
- The ghost is drawn inside `TowerStack`, not as a floating sibling — emitting it in the same `draw_set_transform` block shares the tower's tilt pivot, scroll offset and brick size exactly, and makes desync impossible.
- Cursor hit-testing un-leans the tilt (`_untilt`), or aiming at a point on a leaning tower resolves to the column it would have had upright — a real error at the live-play tilt cap.
- The drag grip lift is in brick units (`drag_grip_offset_units`), an Android-first requirement since a centred ghost puts the thumb over the exact area being aimed at; units keep it proportional when `brick_unit_size` is retuned, and the lifted position feeds the resolution so the ghost docks where the *brick* points, not the thumb.
