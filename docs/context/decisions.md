# Decisions

Scope: why things are built the way they are — rationale, tradeoffs, rejected alternatives, and known constraints. Not a bug tracker; per-doc "Notes" sections carry point-in-time implementation gotchas.

## Politics → Power, Checkpoint → Impact rename

Both gameplay systems were renamed ahead of the production UI design pass to match their production UI names — every wire-protocol field, config key, and Redis-persisted field name was renamed together, not just the docs/code identifiers. **Consequence:** deploy client and server together. A room in flight during that deploy will not restore its Impact/Power state from an old-shaped Redis snapshot.

## Refresh token economy removed

Refresh used to be its own player action gated by a per-player token count (`free_refresh`, capped uses). It is now purely an effect of activating a held `refresh` Power item: no token count, no per-level use cap, fires unconditionally on activation and rerolls **every** player's hand, not just the caster's. The item's id/title dropped "free" as meaningless leftover vocabulary once the cap was gone.

## UI skin-switching system removed

The client used to ship two swappable UI "skins" (`DefaultSkin.tscn` / `Figma_SkinV1.tscn`) with a runtime picker overlay. Both were prototypes, and every scene edit had to be made twice to keep them in sync. Removed ahead of the production UI pass, leaving [Game UI Scene](./ui.md#game-ui-scene) as the one gameplay UI. There is no `ProjectSettings` skin preference or skin-picker node group to keep in sync anymore — if you see references to a skin system, they're stale.

## PointerTriggerRouter removed → native per-trigger signals

A shared `_input()` hit-test router (`PointerTriggerRouter`) used to dispatch taps to popover triggers, because a popover's full-screen `OutsideCatcher` (a later sibling than the triggers) otherwise wins normal GUI hit-testing while a popover is open. It was replaced with each trigger wiring its own native `.pressed` signal (see [coding-conventions.md](./coding-conventions.md)). Investigating a Power-trigger tap bug during this change surfaced the real cause — a same-tap self-close race in [Popover Panel](./ui.md#popover-panel) affecting all four triggers, not something specific to Power's wiring. Fixed via an `OUTSIDE_TAP_GRACE_MS` (250 ms) window on `OutsideCatcher`.

## Team Inventory popover removed → always-visible Team Inventory Panel

The tap-to-open "Team Inventory" popover (`TeamInventoryButton` trigger + `TeamInventoryPopover`) was removed and replaced with a permanently-visible `TeamInventoryPanel` bar in [Game UI Scene](./ui.md#team-inventory-panel), matching a production design reference (`reference/play.png`). The redesign reused the existing `DrawPilePreview`/`DrawPileNameLabel`/`DrawPileCountLabel` nodes verbatim — they previously sat inert in a hidden legacy container — rather than building new nodes or controller logic, so [InventoryController](./ui.md#main-ui-controller) needed no changes beyond the draw-pile preview's color source. `QuickChatTrigger` shifted into the vacated button's screen slot; `PowerTrigger` was left in place. Follow-up bug fixes (all in `InventoryController.update_draw_pile_ui()`/the panel's scene layout, not new features): the draw-pile preview now colors with `players_ctx.local_color()` instead of a fixed `DRAW_PILE_COLOR` constant (removed); the row's labels needed an explicit dark `font_color` override since the shared `CardMetaLabel` theme type has none and defaults to a near-white that's invisible on the panel's white background; the row's `HBoxContainer` alignment is `0` (left) rather than `1` (center) — center alignment crowded the `VSeparator` toward the panel's right edge once the count label's text grew to "Remaining Bricks" phrasing; and `DrawPileNameLabel` always reads the constant `"Next Draw"` rather than interpolating the next block's shape id, since the preview icon already shows the shape visually.

## Tower Stability must stay a pure function

`Tower_Stability.js`'s `settleBlock()`/`evaluate()` must be a pure, deterministic function of the `entries` array — no history, randomness, or hidden state. Two consumers depend on that: the [Balance Simulator](./testing.md#balance-simulator) re-runs it thousands of times and needs reproducible results, and the client re-derives the same tilt from a `game_state` snapshot after reconnecting rather than replaying placement history. Any change to this module must preserve determinism.

## GitHub Pages over Cloudflare Pages for HTML5

Cloudflare Pages was evaluated and rejected: it caps individual files at 25 MiB on every plan (including paid), and the project's `index.wasm` is 35.95 MiB. The cap applies to the stored file, so compression doesn't help, and Workers static assets carry the same limit. The only workaround — serving the wasm from a public R2 bucket with a patched Godot loader — was judged not worth the complexity. GitHub Pages allows 100 MB per file, so it was chosen instead.

**Consequence:** the deployed HTML5 build is public to anyone with the URL; GitHub Pages has no access control. If invite-only playtesting becomes a requirement, itch.io supports restricted projects for free at this file size.

## Pages custom domain must be set manually

Tried automating the `play.tod.galaxxigames.com` custom domain by adding a workflow step that calls `PUT /repos/{owner}/{repo}/pages` with `{"cname": "..."}` using the default `GITHUB_TOKEN` (which the workflow already grants `pages: write`). Rejected: that request failed (curl exit 22 / HTTP 403) because this specific endpoint requires the caller to be a repo admin/maintainer — `github-actions[bot]` never holds that role, regardless of the `permissions:` block. The `pages: write` workflow permission only unlocks the *deployment* API (`actions/deploy-pages` internals), not the Pages *settings* API.

**Consequence:** the custom domain is set once, manually, via Settings → Pages → Custom domain. It's stored as repo config and survives normal deploys and soft-undeploy; a **hard** undeploy deletes the Pages site object and the setting with it, requiring it to be re-added by hand → [build.md § Client HTML5 Pages](./build.md#client-html5-pages).

## Private Asset Pipeline credential split

Cloudflare's R2 S3-compatible endpoint doesn't accept GitHub OIDC federation (unlike the AWS Terraform workflows, which do use OIDC), so this path needs static credentials. The mitigation is a strict read/write split: CI holds an **Object Read only** R2 token (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` secrets) and cannot publish or delete art; only local dev holds an **Object Read & Write** token (gitignored `.env.art`). Publishing (`art-push.sh`) is therefore local and manual by design — automating it would require a write token in GitHub Secrets and defeat the split.

Note on the guarantee's actual scope: art is absent from the repo/history and not browsable from GitHub, but it *is* extractable from a shipped build (`.pck` extractors are commodity tooling; the HTML5 build serves the `.pck` as a public download). `Cor/Art/` is a build input, not a secret — encrypting the PCK wouldn't change this, since the key would ship inside the exported binary.

## Docker EC2 staging removed in favor of K3s

The earlier Docker EC2-1/EC2-2/EC2-3 staging workflows, Terraform, and Ansible have been fully removed. The K3s lab (`infra/k3s`) is the current active stack; see [deployment.md](./deployment.md).

## Caddy gateway ACME cert cache persisted to R2

EC2-GW's `root_block_device` is ephemeral (`infra/k3s/terraform/ec2.tf`) — every `terraform destroy`/recreate of the K3s lab wipes the Docker volume backing Caddy's automatic-HTTPS state (`corp-tower-k3s-caddy-data`), forcing a fresh Let's Encrypt certificate request for `ws.tod.galaxxigames.com` on every rebuild. Repeated destroy/recreate cycles within one week hit Let's Encrypt's "5 duplicate certificates per exact identifier set per 168h" limit, blocking the public WSS smoke test with a `429 rateLimited` until the rolling window cleared — with nothing surfacing the real cause beyond a generic 5-minute smoke-test timeout, since neither the Ansible role nor the deploy workflow checked whether the Caddy container actually stayed up.

Fixed two ways, both in `configure_caddy.yml` / `Server-K3s-Deploy.yml`: (1) a post-start liveness check now fails fast with `docker logs` output instead of waiting out the smoke-test timeout; (2) the ACME cache round-trips through a dedicated Cloudflare R2 bucket (`corp-tower-gateway-state`) around each deploy — restored before Caddy starts, saved after it's confirmed running — so a destroyed-and-recreated gateway reuses the still-valid 90-day cert instead of requesting a new one, and recreates stop counting against the weekly quota. R2 was chosen over AWS S3 specifically to avoid adding AWS IAM scope and reuse the project's existing free R2 usage (see [Private Asset Pipeline credential split](#private-asset-pipeline-credential-split) for the other R2 consumer); the payload is a few KB and R2's free tier has no realistic exposure at this cadence. Full mechanism → [deployment.md](./deployment.md#caddy-gateway-acme-cert-persistence-r2).

Since the archive carries the gateway's live ACME account key and TLS private key, both the GitHub runner and EC2-GW restrict it to `0600` immediately after it's written/received and delete it once consumed, rather than leaving it in shared `/tmp` at default permissions.

**Not yet verified end-to-end** — implemented while blocked on the same rate limit it fixes; first live confirmation is pending the next deploy after the 429 window clears.

## Backup server: separate hostname, and out-of-repo automation

The manual physical backup server (see [deployment.md](./deployment.md#backup-server-manual-physical-machine)) uses `wss://devtod.galaxxigames.com`, not `wss://dev.tod.galaxxigames.com` as first set up. Cloudflare's free Universal SSL certificate only covers the zone apex and *one* level of subdomain (`galaxxigames.com` and `*.galaxxigames.com`) — `ws.tod.galaxxigames.com` never needed Cloudflare's own edge certificate because it's DNS-only (gray-cloud), with Caddy obtaining its own Let's Encrypt cert directly. The backup server's Cloudflare Tunnel is necessarily *proxied* (orange-cloud, Cloudflare terminates TLS at its edge), and a first attempt at `dev.tod.galaxxigames.com` — two levels below the zone apex — hit a bare TLS handshake failure (no certificate for that name at all). Renaming to `devtod.galaxxigames.com` (one level below the apex) fixed it immediately under the existing free wildcard, no Advanced Certificate Manager purchase needed.

Using a wholly separate hostname (rather than cutting `ws.tod.galaxxigames.com` itself over to the backup during an incident) was a deliberate simplification: `ws.` already has two independent Cloudflare DNS updaters (a boot-time systemd oneshot on `EC2-GW`, and a step in `Server-K3s-Deploy.yml`, both writing the same `A` record). A shared-hostname cutover would need careful coordination to avoid one side silently overwriting the other. Two separate DNS names/record types never conflict, at the cost of needing a manual/automatic client-side failover instead of a DNS-level one — see [networking.md § NetworkManager](./networking.md#networkmanager).

The backup server's own automation (`server-backup-{up,down,status}.sh`, `.env.backup`, `cloudflared` config) lives at `~/corp-tower-server-backup/` on the physical machine, **outside** the git repo, for two reasons: it holds live Cloudflare API credentials that must never reach a public GitHub repo, even gitignored; and `actions/checkout`'s default clean step removes untracked/ignored files from the workspace on every run, so anything gitignored *inside* the repo checkout would be wiped out by the very next CI run regardless. Only the two workflow YAML files live in the repo (no secrets referenced), calling the external scripts by absolute path on a GitHub Actions self-hosted runner registered on that machine (label `backup`).

Two further simplifications, both deliberate: (1) the backup runs a single Docker container with no `REDIS_URL` set, relying on `Redis_State.js`'s built-in single-instance in-memory fallback rather than standing up Redis — correct for one physical machine, not for the multi-replica K3s case; (2) the deploy workflow checks for `docker`/`cloudflared` and fails with instructions if missing, rather than auto-installing them via `sudo` — avoids needing a passwordless-sudo rule on the machine purely to satisfy a non-interactive CI job, at the cost of one-time-only manual installation. Relatedly, `cloudflared` runs as a **user-level** systemd service (not `cloudflared service install`'s system-wide default) specifically so `systemctl --user start/stop` needs no `sudo` at all — a self-hosted runner job has no TTY to answer a password prompt, which surfaced as a real failure (`sudo: a terminal is required`) before this was caught. `loginctl enable-linger` was required once so the user service instance runs even when the runner isn't an interactive login session.

## Automated Master fast deploy routes to whichever server is up

`Server-K3s-Automated-Master.yml`'s fast path (`fast_k3s_deploy == true`) used to call `Server-K3s-Deploy.yml` unconditionally. If the K3s stack was down (the exact scenario the physical backup exists for), this failed opaquely inside `generate_k3s_inventory.py` — it raises `SystemExit` when it can't find exactly one running `k3s-control-plane`-tagged instance, well after the workflow had already started AWS/SSH setup, with no indication that the physical backup was a viable alternative.

Fixed by adding `check-k3s-status` (queries `aws ec2 describe-instances` the same way `Server-K3s-Deploy.yml`'s own target-resolution step does, checking specifically for a running `k3s-control-plane` instance) ahead of the deploy job, and routing on its result: K3s up → `k3s-deploy-fast` as before; K3s down → `check-backup-status` checks the physical backup's `corp-tower-server` Docker container via `docker ps` (the same filter `server-backup-common.sh`'s `stop_cloudflared_if_idle` already uses internally), then `backup-deploy-fast` calls `Server-Backup-Deploy.yml` if it's up; neither up → `fast-deploy-unavailable` fails loudly with an explicit message instead of the previous opaque crash. `Server-Backup-Deploy.yml` gained a `workflow_call` trigger (in addition to its existing `workflow_dispatch`) so the Automated Master can invoke it directly.

Deliberate ordering: `check-backup-status` only runs (and only then touches the self-hosted `backup`-labeled runner) when `check-k3s-status` has already reported K3s down. Checking backup status unconditionally on every fast-path run would mean an ordinary, healthy K3s push could stall waiting on the physical backup machine's runner to be online — self-hosted runner jobs queue indefinitely if no matching runner is available, with no automatic queued-job timeout. Gating it behind a confirmed-down K3s keeps the common case (K3s healthy) fully independent of the physical machine's availability.

## Web (HTML5) backup: dedicated hostname, not shared with GitHub Pages

The web (HTML5) backup on the same physical machine (see [deployment.md § Web (HTML5) backup](./deployment.md#web-html5-backup)) first tried reusing `play.tod.galaxxigames.com` itself — GitHub Pages' own custom domain — cutting its Cloudflare CNAME over to the backup's tunnel during an undeploy and back afterward, since nothing else automates that record (unlike `ws.tod.galaxxigames.com`'s two independent updaters, see the entry above). This hit exactly the same certificate-depth limit already documented for `dev.tod` vs `devtod`: Cloudflare's free Edge Certificate only covers the zone apex and *one* level of subdomain, and `play.tod` is two levels deep. It happened to work while pointed at GitHub Pages (a certificate for that exact hostname already existed from whenever the custom domain was first configured), but cutting the *same* proxied hostname over to the Cloudflare Tunnel surfaced `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` — Cloudflare's edge, not GitHub's, terminates TLS for a proxied record, and the existing certificate didn't cover the tunnel-facing configuration. The dashboard's fix (enable Total TLS) requires purchasing the Advanced Certificate Manager add-on — a recurring cost, not something to take on silently on the user's behalf.

Given the cost, the design reverted to the same pattern as `devtod`: a wholly separate, one-level-deep hostname, `devplay.galaxxigames.com`, sharing the WS backup's existing Cloudflare Tunnel via a second `ingress` rule (no second tunnel needed). `play.tod.galaxxigames.com` and its GitHub Pages custom-domain setting are untouched by the web backup entirely.

The "only one live at a time" policy coupling was originally baked directly into the base workflows (`Client-HTML5-Undeploy.yml`'s `failover_to_backup` and `Client-HTML5-Pages.yml`'s `stand_down_backup` inputs, both defaulting on), even though the two hostnames can no longer technically collide the way a shared record could. This was pulled back out: baking the pairing into the base workflows meant `Client-HTML5-Pages.yml`, `Client-HTML5-Undeploy.yml`, `Client-HTML5-Backup-Deploy.yml`, and `Client-HTML5-Backup-Cleanup.yml` could never be dispatched independently without also toggling the other side, which stopped both from ever being intentionally live at once (e.g. testing the backup while Pages stays up). The coupling then moved into a dedicated orchestration workflow, `Client-HTML5-Set-Live-Host.yml`, which explicitly chained the pair of calls itself — but confirmed live operation showed `play.tod.galaxxigames.com` and `devplay.galaxxigames.com` running simultaneously without issue, so the "only one live" policy itself was dropped and `Client-HTML5-Set-Live-Host.yml` was deleted. The four base workflows have no knowledge of each other and run — or stay live — independently and simultaneously, with nothing left to pair them.

## Auto-deploy guard rails check live status, not a stored flag

`Client-HTML5-Pages.yml` gained a `push` trigger (previously `workflow_dispatch`/`workflow_call`-only, see [build.md § Client HTML5 Pages](./build.md#client-html5-pages)) so it auto-deploys on client pushes the same way `Client-HTML5-Backup-Deploy.yml` already did. Without a guard, that auto-deploy would silently undo an intentional `Client-HTML5-Undeploy.yml` run (or an intentional `Client-HTML5-Backup-Cleanup.yml` stand-down) the next time someone pushed to `src/Client/**`.

Both workflows now gate their `push` trigger behind a job that checks the target's actual live state, rather than a stored flag a separate workflow would have to remember to set: `check-pages-status` `curl`s `https://play.tod.galaxxigames.com/` directly and treats a `404` (hard-undeploy) or a body matching the soft-undeploy placeholder text ("Corp Tower is offline") as not-deployed; `check-web-backup-status` runs `docker ps` for the running `corp-tower-web` container on the self-hosted `backup` runner. This is the same live-status-check pattern `check-k3s-status`/`check-backup-status` already use (see [Automated Master fast deploy routes to whichever server is up](#automated-master-fast-deploy-routes-to-whichever-server-is-up) above) — a runtime check can't drift out of sync the way a manually-toggled flag could.

This is deliberately **not** a reintroduction of the cross-workflow coupling removed in the entry above: each guard only inspects its *own* target's live state, never the other host's — `play.tod.galaxxigames.com` and `devplay.galaxxigames.com` still deploy, stand down, and stay live fully independently of each other. The guard also only gates the `push` trigger; manual `workflow_dispatch` always runs regardless of live state, so an intentional redeploy after an undeploy/stand-down still works exactly as before.

## A skipped guard job cascades to skip downstream jobs unless their `if` says otherwise

Adding `check-pages-status` ahead of `build` in `Client-HTML5-Pages.yml` (see [above](#auto-deploy-guard-rails-check-live-status-not-a-stored-flag)) broke manual `workflow_dispatch` deploys: `build` correctly ran and succeeded (its `if` explicitly treats `needs.check-pages-status.result == 'skipped'` as OK, since that job only runs on `push`), but `deploy` — `needs: build`, no explicit `if` — was skipped on every manual dispatch regardless of Pages' live state. Confirmed live via the Actions API across several `workflow_dispatch` runs: `build: success`, `deploy: skipped`.

Cause: a job's default `if` (when omitted) is `success()`, and `success()` evaluates against the job's **entire upstream dependency graph**, not just its direct `needs` — a skipped job anywhere in that ancestry (here, `check-pages-status`, an ancestor via `build`) makes it evaluate false, even though the job's direct dependency (`build`) itself succeeded. `Client-HTML5-Backup-Deploy.yml`'s equivalent `deploy-to-backup` job already had `if: always() && needs.build.result == 'success'` for this exact reason and was unaffected; `Client-HTML5-Pages.yml`'s `deploy` job was missing that same guard. Fixed by adding `if: always() && needs.build.result == 'success'` to `deploy`. Any job placed downstream of a conditionally-skipped job needs this pattern explicitly — omitting `if` is not equivalent to "run when my direct dependency succeeds."

## Nested reusable workflows can't detect their own trigger via event name

While wiring the automatic coupling (originally `Client-HTML5-Undeploy.yml` → `Client-HTML5-Backup-Deploy.yml` and `Client-HTML5-Pages.yml` → `Client-HTML5-Backup-Cleanup.yml`; the pairing later moved into a dedicated `Client-HTML5-Set-Live-Host.yml` orchestration workflow, then was deleted entirely once "only one live" stopped being the policy — see the entry above), each backup workflow's manual-dispatch confirmation gate (`CLEANUP_WEB_BACKUP`, and `Client-HTML5-Undeploy.yml`'s own `UNDEPLOY` guard) needed to be skipped when the workflow was invoked automatically as a reusable `workflow_call`, since the caller never had that confirmation string to pass through. The first attempt gated this on `if: github.event_name == 'workflow_dispatch'` — this does **not** work: `github.event_name` reflects the *top-level* run's trigger event, unchanged no matter how many levels of `workflow_call` nesting the current job is inside. Since every workflow in this chain was ultimately kicked off by a human `workflow_dispatch`, every nested job saw `event_name == 'workflow_dispatch'` too, so the confirmation guard ran (and failed) even on the fully-automated path — the first real test of the automatic failover failed for this reason before ever reaching the backup machine.

Fixed by using an explicit input instead of ambient context: an `invoked_via_call` boolean, declared only under each workflow's `on.workflow_call.inputs` (default `true`, never declared under `workflow_dispatch`), checked via `if: inputs.invoked_via_call != true`. This worked because `inputs.*` genuinely is scoped per-invocation (unlike `github.event_name`) — a direct `workflow_dispatch` run simply never has that input defined at all. **Since removed:** once `Client-HTML5-Set-Live-Host.yml` (the only caller) was deleted, `workflow_call` triggers and `invoked_via_call` inputs were stripped from `Client-HTML5-Undeploy.yml` and `Client-HTML5-Backup-Cleanup.yml` too (`Client-HTML5-Backup-Deploy.yml`'s `workflow_call` had no confirmation gate, so it just lost the trigger, nothing else) — the guard jobs now run unconditionally, gated only by their `workflow_dispatch` confirmation string. This decision record stays as the reference for the underlying `github.event_name` nesting gotcha, should a future reusable-workflow chain need it again.

## DNS cutover verification must use the Cloudflare API, not `dig`, for proxied records

`server-backup-common.sh`'s `wait_for_cname` helper (shared by both the WS and web backups' up-scripts) originally polled `dig +short $name CNAME` after a Cloudflare DNS upsert, to confirm the cutover actually took effect rather than trusting a bare API 200. This produced a false failure on the web backup's very first successful end-to-end run: Cloudflare **never exposes a literal CNAME to public resolvers for a proxied (orange-cloud) record** — it resolves the hostname straight to its own anycast A/AAAA addresses instead, regardless of what the record's `content` actually is. `dig CNAME` against a correctly-configured proxied record is therefore always empty, and the wait loop always timed out and `die`d — even though a direct Cloudflare API query confirmed the record was exactly right, and the site was already reachable and working.

Fixed by having `wait_for_cname` re-query the Cloudflare API (the same `dns_records?type=CNAME&name=...` lookup `upsert_cloudflare_cname` already uses) and compare `.result[0].content` directly, dropping `dig` from these scripts' `require_cmd` lists entirely. This is also more correct in principle: the Cloudflare API reflects a write immediately (no public DNS propagation delay to wait out), so the retry loop is now just a small safety margin against a transient API read, not a genuine convergence wait. The same misleading `dig`-based display existed in both `server-backup-status.sh` and `web-backup-status.sh`'s read-only DNS section and was fixed the same way, so operator-facing status output doesn't show a healthy record as blank/broken.

## EKS kept plan-only

The EKS path (`infra/eks`) is Terraform **plan only** — deliberately not applied. Two reasons: (1) managed AWS resources in this path may exceed free-tier expectations, so plan output and cost need review before any apply/deploy workflow is added; (2) the NLB target group has no pod/node registration mechanism yet (no Load Balancer Controller or IRSA OIDC provider exists in this Terraform root), so applying it wouldn't produce working ingress yet regardless of cost.

## Argo CD prepared but not enabled

Argo CD bootstrap manifests exist (`infra/k3s/argocd/bootstrap`) but nothing installs or applies them in the first K3s rollout. Planned enablement path: install → one manual sync → a rollback test succeeds → only then turn on automated prune/self-heal. `GITHUB_TOKEN` is not a suitable long-lived Argo CD repo credential for private repos; a persistent repo-read credential is needed instead. **Known bug to fix before enabling:** `infra/k3s/argocd/bootstrap/application.yaml`'s `spec.source.targetRevision` is currently pinned to an already-merged feature branch instead of `main` — harmless while unapplied, but would track the wrong ref the moment Argo CD is turned on.

## Debug menu / debug config not yet gated

The floating debug overlay is present in every client build (no build flag, no `SHOW_DEBUG_UI`-style constant) and is only *disabled* (not hidden) until a room connects. Server-side, `update_config`/`resetDebugConfig` have no admin/auth check beyond the existing message-validation rules. **This must be gated — behind a build flag, QA account permission, or server-side admin authorization — before public release.** Tracked from both the design side (GDD) and the technical side (TDD future work); stated once here.

## Debug menu category navigation switched from tabs to a dropdown

Adding an 8th category (**Parallax**, see [ui.md](./ui.md#leaf-components) `DebugPanelController`) to the debug overlay's `TabContainer`-based navigation made the tab-header row visibly cramped — a user-reported "already starting to become cluttered" concern anticipating further categories being added later. Replaced `TabContainer` (`DebugTabs`) with a plain `Control` (`DebugCategoryPanels`) holding the same category `ScrollContainer`s stacked full-rect on top of each other, paired with a `DebugCategoryDropdown` `OptionButton` that toggles `.visible` on exactly one category at a time (`DebugPanelController.on_category_selected()`). Chosen over just shrinking tab labels or wrapping the tab row: a dropdown scales to an arbitrary number of categories with zero added header space, matching that debug categories are expected to keep growing. Each category's internal content (labels, sliders, `OptionButton`s) and their `configure_slider()`/`apply_config()` wiring were left untouched — only the outer navigation chrome changed, since `TabContainer`'s children already filled the tab-content rect the same way the new plain `Control`'s children now do explicitly via full-rect anchors.

Each Parallax-category row's name is a flat `Button` (not a `Label`, unlike every other category) so it can be tapped to open a per-variable explainer — see **Debug Tooltip** below.

## Debug Tooltip: a purpose-built dimmed popup, not a reuse of Popover Panel

The Parallax category's calibration variables (`scroll_start_ratio`, `scroll_ease_power`, etc.) aren't self-explanatory from a slider alone, so each row's name button opens a short designer-facing description on tap. [Popover Panel](./ui.md#popover-panel) already implements the "tap outside to close, with a grace period so the opening tap doesn't immediately close it" pattern used elsewhere (Chat/Power/Quest popovers), but its `OutsideCatcher` is transparent — those popovers are anchored corner cards over live game content, so dimming the rest of the screen would be wrong for them. The debug tooltip is conceptually a modal explainer over an already-modal debug panel, where dimming everything behind the card (including the debug panel itself) reads correctly. Rather than adding a dim option to the shared `PopoverPanel.gd`/`.tscn` (risking behavior changes to the three existing popovers), a small dedicated `DebugTooltip.gd` was added that mirrors Popover Panel's outside-tap/grace-period shape (`OUTSIDE_TAP_GRACE_MS`) but adds an actual semi-transparent `ColorRect` dim layer, keeping the two components' behavior contracts independent.

## No persistent leaderboard yet

Redis is active-session state (matchmaking/reconnect/room snapshots), not long-term persistence. There is no durable leaderboard or player-stat storage yet — planned future technical work, along with structured logging. Multi-worker matchmaking now has integration-level regression coverage (see [testing.md](./testing.md#server-matchmaking-queue-tests)); reconnect/gateway routing across pods more broadly is still untested at that level.

## Matchmaking queue lost-update and cross-pod room-delivery gap

Reported symptom: when two players joined from the same network at nearly the same moment (plus a third player from elsewhere), only one of the two made it to the play screen. Player identity was already `playerId`/`reconnectToken`-based, not IP-based, so the cause was elsewhere. Two independent multi-pod bugs were found and fixed together in `Lobby_Manager.js`/`Redis_State.js`:

1. **Lost-update race in the shared queue.** `tryCreateRoom()` used to read the entire Redis matchmaking queue, then unconditionally overwrite it (`replaceQueue()`: `DEL` + rewrite). `addPlayer()` calls `enqueuePlayer()` (an unlocked `lPush`) *before* acquiring the matchmaking lock, so if another pod's `enqueuePlayer()` landed in the gap between one pod's read and its full-queue rewrite, that player's entry was silently wiped from Redis — they stayed connected but never got queued into any room. Fixed by replacing the read-all/rewrite-all pattern with `dequeueRealPlayers(maxCount)` (atomic `RPOP ... count`) and `requeuePlayers(players)` (atomic `RPUSH` of only what was actually taken back out) — neither can clobber an entry it never touched. `replaceQueue()` was deleted rather than kept as a fallback, since its read/write gap was the actual defect.
2. **Cross-pod delivery gap.** Whichever pod wins the matchmaking lock is the one that runs `createRoom()`, but with 2 server replicas behind round-robin, that pod only holds live WebSocket references for players connected to itself — a teammate connected to a different pod got added to the room's player list server-side, but the direct `sendPlayer()` call silently no-op'd (`ws` was `null` locally), so `room_created` never reached them and their socket just sat open and silent. Fixed by publishing a lightweight `player:assignments` pub/sub event (`Redis_State.js`'s `publishPlayerAssignment`/`subscribeToPlayerAssignments`) whenever a room-assigned player isn't locally connected; the pod that actually owns that player's socket receives it and calls `resumePlayer()`, reusing the same `hydrateRoom()`/room-channel-subscribe path already relied on for genuine reconnects, rather than inventing a parallel state-relay mechanism.

Regression coverage: [Server Matchmaking Queue Tests](./testing.md#server-matchmaking-queue-tests).

## Fixed brick size + parallax scroll replaces shrink-to-fit tower rendering

[Tower Stack](./ui.md#leaf-components) used to keep the whole tower on screen by shrinking brick size to fit (`MIN_UNIT_SIZE`/`MAX_UNIT_SIZE`, a fit-to-box formula in `_unit_size()`), which made bricks visibly smaller than their designed size on tall/overbuilt towers. Requested fix: bricks must stay the designed size (`BRICK_UNIT_SIZE`, 34px) always; once the tower's top approaches the [Top Indicator](./ui.md#main-ui-controller), the view should instead scroll/pan up, like a camera panning up the tower, with HUD elements staying fixed and only the tower + background moving. The scroll/clip machinery this needed (`_scroll_offset_units()`, `_visible_unit_capacity()`, `_is_rect_visible()`) already existed in `TowerStack.gd` — it previously only activated in the rare case where shrink-to-fit bottomed out at `MIN_UNIT_SIZE`; removing shrink-to-fit made it the primary, always-available mechanism instead of new code being written.

The background reveal reuses the existing full-screen `Background` `Panel` (solid sky-blue, already sitting behind `BgArt`) as the "extra sky" revealed when [Background Parallax](./ui.md#leaf-components) pans `BgArt` down — no new node was needed for a placeholder fill. This was an explicit interim choice: new painted background art is expected later once the mechanic is confirmed working. Because a flat color has no edge, it supports pan of any distance; the real art replacement must be a seamlessly vertically-tileable sky/cloud texture (top edge matches bottom edge) to preserve that property, rather than just a taller static image.

**Revised (2026-07-25): pan is now capped at `target_height`, not unlimited.** The original ratio-based trigger (`SCROLL_TRIGGER_RATIO`) pinned the tower's top well short of the Top Indicator, leaving a large unused gap, and kept panning indefinitely as a tower was overbuilt. Requested fix: the pinned row should sit as close under the Top Indicator as the fixed 34px brick grid allows (a few px gap is acceptable — bricks don't subdivide, so exact zero-gap isn't achievable), and panning should stop once the tower reaches `target_height` (perfect fit) rather than continuing to compensate for overbuild. Implemented by replacing `SCROLL_TRIGGER_RATIO` with `TOP_INDICATOR_CLEARANCE_UNITS` (1 brick unit reserved off the visible capacity) and capping `_scroll_offset_units()`'s focus height at `target_height` when set. Net effect: once a tower is overbuilt, the excess bricks are no longer compensated for and rise above the frozen top into the Top Indicator's screen area — visible there rather than clipped, because `GameUI.tscn`'s existing node order already draws `TopIndicatorRow` after `TowerStack` (indicator on top), so overbuilt bricks appear to pass underneath/behind the indicator bar instead of covering it. That node order was deliberately left unchanged — an earlier attempt at this fix reordered the nodes so the tower drew *above* the indicator, which was wrong: the requirement is for overbuild to tuck under the bar, not cover it.

The original "only scroll once the tower completely fills the visible area" trigger (with a fixed `SCROLL_HEADROOM_UNITS` jump) was replaced with `SCROLL_TRIGGER_RATIO` (calibrated to 0.65) so the parallax visibly starts partway up the screen rather than only once bricks are about to hit the Top Indicator — a user-requested calibration, ramping continuously from 0 with no jump at the trigger point. (Since renamed to the `scroll_start_ratio` export var, recalibrated to 0.7 — see the two-phase-ease revision below.)

**Revised again (2026-07-25): two-phase eased ramp, restoring a start threshold, plus full debug-menu tunability.** The single-value `TOP_INDICATOR_CLEARANCE_UNITS` trigger above pinned the tower's top to the same fixed screen row for the *entire* climb once past the trigger — any height above that row snapped straight to it — so the tower looked "close to the bar" after only a handful of bricks, long before target height, undermining the intent that the bar represents the target height specifically. Fixed by splitting the trigger back into two knobs: `scroll_start_ratio` (0.7, restoring the pre-revision ratio-based start-of-scroll point, now purely a "no scroll below this" threshold) and a new `scroll_ease_power` (3.0) — a `pow(progress, power)` cubic ease-in applied to the row's approach from the start row toward the flush row as `current_height` nears `target_height`, so the camera holds back for most of the climb and only visibly closes the gap in the final stretch, rather than drifting the whole way at a constant rate. Separately, `scroll_start_ratio`, `scroll_ease_power`, `top_indicator_clearance_units`, `brick_unit_size`, `drop_duration`, `drop_height_units`, `tilt_ease_speed`, `collapse_tilt_deg`, `top_padding`, and `bottom_padding` were converted from `SCREAMING_SNAKE_CASE` consts to lowercase `@export var`s on `TowerStack.gd`, purely so the Debug Overlay's new **Parallax** category (see [ui.md](./ui.md#leaf-components), `DebugPanelController`) can tune them live — client-side only, no server round-trip, since these are cosmetic rendering values rather than `Game_Config` keys. `TowerStack.refresh_visuals()` was added so the debug panel can force a recompute + redraw after changing one live.

`PlatformArt` (the ground platform under the tower) was initially left untouched on the assumption it should stay screen-fixed like HUD. Testing showed the opposite was wanted: per the original request, the platform is conceptually part of the *background*, not the HUD, so it should recede with the parallax and eventually scroll out of view for an arbitrarily tall/overbuilt tower, same as the sky. Fixed by attaching `BackgroundParallax.gd` to `PlatformArt` as a second instance, which required converting its previously-hardcoded `PARALLAX_RATIO`/`EASE_SPEED` consts to `@export var parallax_ratio`/`ease_speed` so each attached instance can be tuned independently from the Inspector rather than sharing one script-wide value. Current tuning: `BgArt` (sky, script default `0.3`) moves slower than `PlatformArt` (ground, overridden to `1.1`) — the platform needs to move *faster* than the tower's own 1:1 scroll rate specifically so it doesn't lag behind and visually desync/gap from the tower's receding base.

Once the platform started receding, the tower appeared to float: `TowerStack`'s oldest bricks were being culled at the Control's own fixed rect boundary (`clip_contents = true`, and `_is_rect_visible()`'s bottom bound was the Control's own `size.y`), while the ground kept sinking away below that fixed line, opening a visible gap. Fixed by removing `clip_contents` and extending `_is_rect_visible()`'s bottom bound to the actual screen bottom (`get_parent().size.y - position.y`, i.e. `PlayField`'s full height in `TowerStack`'s local coordinates) — the tower's own rect, baseline, and scroll-trigger math are unchanged, only how far down old bricks continue to be drawn. They're now hidden only once a later-drawn sibling (the `ActionRow` inventory buttons, starting at `offset_top = 827`) visually covers them, not by an arbitrary early clip.

**Revised (2026-07-25): `PlatformArt` now tracks the tower's scroll in exact 1:1 lockstep instead of an approximate faster ratio.** The `1.1` ratio described above was a deliberate but approximate compensation for `BackgroundParallax.gd` always easing toward its target via `lerpf`, while `TowerStack`'s own brick-scroll offset applies instantly (no easing) on every `set_tower()` call. A constant ratio multiplier can't correctly cancel an easing-induced lag in general: the gap between the lowest brick and the platform worked out to `-7 + 0.1 * scroll_pixels` — a healthy overlap at low scroll, but growing without bound once scroll passed ~70px (~2 brick units) — which is why this wasn't durably fixed by six-plus rounds of prior ratio/offset "calibration" commits, and why the tower still visibly floated above the platform on taller towers. Fixed by (1) setting `PlatformArt.parallax_ratio` to `1.0` (exact match to the tower's own scroll rate) and (2) adding a per-instance `@export var instant: bool` to `BackgroundParallax.gd` that, when true, snaps `displayed_offset`/`position.y` straight to the target inside `set_scroll_pixels()` instead of waiting for the next `_process()` lerp tick — set `instant = true` only on `PlatformArt`, so it moves in the same frame as `TowerStack`'s brick redraw with zero catch-up lag, leaving a constant small (~7px) art overlap at any scroll depth instead of a growing gap. `BgArt` is untouched (`instant` defaults to `false`; its ratio stays at the script default `0.4` — corrected here from the `0.3` this doc previously stated, which didn't match any actual per-node override in `GameUI.tscn`), since its slower eased sky pan is a cosmetic depth effect with no ground-contact alignment requirement. A `Camera2D`/viewport-follow redesign was considered and rejected for this fix — the client is entirely `Control`-node/UI-canvas based (412×917 `canvas_items` stretch) with `TowerStack` rendering bricks via raw `_draw()` calls, not `Node2D` children a camera could pan across, so that would have meant re-architecting `TowerStack`/`BlockPreview`/`BackgroundParallax` and the drag/lane hit-testing math for a bug that was fully fixable as a scalar/timing correction within the existing parallax-script pattern.

## Five fixed bricks + 3-lane placement replace the size ramp

The production UI (`reference/play.png`) drove a ground-up gameplay-logic redesign; it **supersedes** the size-1..6 block system above.

- **5 fixed bricks (`I`/`O`/`L`/`T`/`Z`, all 4-cell), available from level 1.** The `blockShapeVariants`/`blockUnlockLevels`/`blockWeights` size ladder and the `createRandomUnlockedBlock`/`getWeightedUnlockedBlockSize`/`isBlockSizeUnlocked` helpers were removed in favor of a flat `brickShapes` + `brickWeights`. Difficulty now comes from target height, timer, stability, and lane play, not shape unlocks.
- **3 lanes on a narrow grid.** `towerGridWidth` went 7 → 5 (later widened again to 9 — see [Random rotation, 9-column lane grid, and per-instance random anchor](#random-rotation-9-column-lane-grid-and-per-instance-random-anchor)); the player aims at lanes L/C/R, and wide bricks can spill into outer overflow columns. Chosen because the reference tower reads as a narrow interlocking grid (a `T` balancing on its center stem is exactly a grid brick supported only in the middle). `Tower_Stability.settleBlock` no longer auto-centers — it takes a caller-supplied `originX` (from `Game_Engine.resolveLaneOriginX`), so the player's lane is the new placement input. The narrow base makes tall towers tippy on purpose: the game rewards building wide bases.
- **Stability kept pure, extended with a signed lane-imbalance term** (`towerLaneImbalanceWeight`) alongside CoM + overhang — must stay deterministic ([Tower Stability must stay a pure function](#tower-stability-must-stay-a-pure-function)).
- **Scoring overhaul** toward "help fill the Impact + reach target height, especially exact finish": placement stays the contribution earner; precision/team-exact bonuses were raised (20/15); the plain finisher bonus was zeroed so **overbuild finishing earns nothing**; a new **Impact-fill bonus** pays at each passed Impact scaled by contribution over the band requirement. Implemented mostly via config values plus one new `Impacts.awardImpactFillBonus`; `startLevel()` now preserves already-queued score events so the fill-bonus popup survives the level transition.

**Known gaps / in progress:**
- **Balance tuning ongoing** — high-level completion is low in the greedy [Balance Simulator](./testing.md#balance-simulator) because that bot builds narrow, tippy towers; the target-height curve + stability weights still need a tuning pass (aided by the live debug menu). Stability defaults: `towerOverhangWeight` 0.15, `towerLaneImbalanceWeight` 0.1, `towerCollapseTiltScore` 4.0.
- The four items formerly planned here (client lane-guide overlay, ghost→real drop/snap animation, no-unintended-gap check, random-rotation bricks) are now done, including the lane-grid/anchor follow-up random rotation required — see [Random rotation, 9-column lane grid, and per-instance random anchor](#random-rotation-9-column-lane-grid-and-per-instance-random-anchor) below.

## Random rotation, 9-column lane grid, and per-instance random anchor

Follow-up to [Five fixed bricks + 3-lane placement](#five-fixed-bricks--3-lane-placement-replace-the-size-ramp) once its four "planned next" items landed.

- **Random rotation is live.** `Block_Supply.getRotations`/`createBlock` pick a random rotation of the drawn shape at creation (still not player-rotatable after dealing); `Game_Config.brickShapes` cells define only the canonical orientation now. Effective height/width varies 1–4 by the rotation drawn (e.g. horizontal `I` is height 1, width 4) instead of the old fixed per-shape height.
- **Client rendering moved from per-cell rects to a single rotated textured quad.** `BlockData.gd` gained `brick_texture`/`brick_shader_material` (per-shape PNGs in `Cor/Art/Bricks/`, shaded by `Cor/Shaders/BrickShade.gdshader` — a simple top-lighter/bottom-darker vertical gradient over the player-color modulate) and `detect_rotation_steps`/`brick_quad_points` (replicates the server's rotation math so the client can rotate the canonical texture to match a randomly-rotated placed/drawn block). `TowerStack` and `BlockPreview` both draw through this; the old per-cell-rect fallback path is kept only for when a shape has no texture.
- **The prior vertical-flip bug is fixed** — `TowerStack`/`BlockPreview` now render true server geometry (e.g. a `T` rests on its stem, not upside-down), and lane guides + a ghost→real drop animation are live during placement.
- **Grid widened 5 → 9 columns, lanes moved to columns 3/4/5** (`towerGridWidth`, `placeableLanes`). Root cause: the old fixed-anchor formula (`floor((width-1)/2)`, same column regardless of lane) combined with random rotation meant a width-4 horizontal `I` placed at the R lane needed an `originX` one column past the old 5-wide grid's edge (`maxOriginX` was 1, needed 2) — a hard clamp bug that silently shrank the R lane's placement to match Center's. Widening to 9 columns (margins 0–2 / 6–8, lanes still 1 apart at 3/4/5) gave enough room.
- **Anchor is now a per-block random property, not a formula.** `Block_Supply.getRandomAnchorX` picks uniformly among the drawn rotation's column range at creation (e.g. a 2-wide `O` anchors on column 0 or 1, chosen at random); `Game_Engine.resolveLaneOriginX` reverted to the simple `originX = laneCol - block.anchorX` (no per-lane logic). Two alternate designs were tried and rejected first:
  - *Contextual per-lane anchor* (leftmost cell for L, rightmost for R, middle for C, recomputed per lane rather than stored on the block) looked appealing but, combined with lanes only 1 column apart, collapsed most brick widths onto identical placements regardless of which lane was picked — width-3 bricks (the majority of `L`/`T`/`Z` rotations) produced the exact same placement on all three lanes.
  - *Widening lane spacing* (e.g. guides 3 columns apart instead of 1) fixed that collision but was rejected in favor of keeping lanes 1 apart.
  - The random-fixed-anchor design avoids the collision as a side effect: since the anchor is constant per block regardless of chosen lane, `originX` always differs by exactly the lane spacing between L/C/R, so all three lanes stay distinct for every brick width without needing wider lane spacing.
- **No anchor-indicator art exists yet.** `reference/guide-only-brick-emoji.png` is a whole-brick design mockup, not an importable asset. `BlockPreview._draw_anchor_marker`/`_draw_smiley` draw a placeholder marker (circle + dot eyes + arc mouth) over the brick's anchor column in the inventory card and drag preview, to be swapped for real art later; the stability-mood-emoji concept is deferred to a future session. Full detail → [ui.md § Leaf components](./ui.md#leaf-components).

**Superseded (see below):** the lane/anchor system this section describes was fully replaced by 14-column corner-snap placement.

## 14-column corner-snap placement replaces lanes and anchors

Follow-up game-logic redesign requested directly (not driven by a new reference mockup this time). **Supersedes** [Five fixed bricks + 3-lane placement](#five-fixed-bricks--3-lane-placement-replace-the-size-ramp) and [Random rotation, 9-column lane grid, and per-instance random anchor](#random-rotation-9-column-lane-grid-and-per-instance-random-anchor) for everything placement-related; random rotation itself (`Block_Supply.getRotations`) is untouched.

- **Grid widened 9 → 14 columns; only columns 4–9 are placeable**, a **hard exclusion** with no overflow/spillover (`Game_Config.towerGridWidth` = 14, `placeableColumnMin`/`placeableColumnMax` = 4/9, replacing `placeableLanes`). This is a deliberate simplification versus the old lane system, where wide bricks anchored near a lane's edge could spill into the outer "overflow" columns — the exact mechanism behind the old 5→9-column widening's hard-clamp bug (see the superseded section above). Requiring the *entire* footprint to fit the placeable range up front removes that whole bug class.
- **The random-anchor mechanic is removed entirely**, not just re-tuned. `Block_Supply.getRandomAnchorX` and the `anchorX` field are gone from created blocks; `Game_Engine.resolveLaneOriginX` is replaced by `getPlaceableOriginRange(block)` (valid origin-column range for the brick's width) and `resolveColumnOriginX(block, column)` (clamps a requested column into that range). The wire message field changed from `lane` (`left`/`center`/`right`) to `column` (integer) in `place_block`. Rationale: with direct corner-to-point snapping, a brick's own geometry already determines where it lands — the anchor cell was only ever needed to bridge between a 3-way discrete lane choice and a per-shape-random reference point, and that bridge is no longer needed once placement is continuous.
- **Corner-snap placement.** The platform has 7 fixed snap points, one per column boundary spanning the placeable range. The client (`TowerStack.update_snap_preview`) maps the cursor to a fractional column, enumerates every valid integer origin column for the dragged brick's width, and picks whichever candidate's nearer edge (left or right) is closest to the cursor — this is "nearest corner snaps to nearest point," resolved in grid space rather than by literal corner-pixel distance (which is degenerate for a cursor-centered drag ghost, since all corners are always equidistant from a perfectly centered cursor). The resolved column is authoritative-checked server-side via the same clamp (`resolveColumnOriginX`), so nothing the client picks can ever be surprisingly re-clamped.
- **Snap-point dots distinguish object, not selection state.** Filled dots mark the platform's 7 points and every corner of already-placed bricks (drawn by `TowerStack`); hollow dots mark the dragged ghost's own corners (drawn by `BlockPreview`, `FLOATING_DRAG` mode only). There is no separate "this is the active target" highlight — the player judges alignment by proximity between a hollow (ghost) dot and a filled (platform/tower) dot, the same way magnetic-snap indicators work in design tools. Both dot styles use **true outline vertices** (`BlockData.outline_corners` — a lattice point belongs to a polyomino's silhouette iff an odd number of the up-to-4 touching cells are occupied; none of the 5 tetromino shapes touch only diagonally, so this simple parity rule is exact), not bounding-box corners — a bounding box would put dots on phantom corners `L`/`T`/`Z` don't actually occupy. Placeholder red-dot art only; no real snap-point asset exists yet, same as the smiley it replaces.
- **Spawn-height-driven drop animation.** Previously the "drop" animation was a fixed, arbitrary 6-unit fall (`drop_height_units`, an `@export` since [the parallax-tunability pass](#fixed-brick-size--parallax-scroll-replaces-shrink-to-fit-tower-rendering)) unrelated to any real spawn position — the server never modeled a spawn height at all, placement was always instant/analytic. Replaced with a formula: spawn top edge = platform top (height 0) + the tower's global-peak height *before* this placement + 2× the placed brick's own height. `TowerStack._compute_drop_fall_units` derives the actual fall distance from that formula minus the brick's real landed position, so taller towers produce visibly longer falls. `drop_height_units` was removed as an export (and its Parallax-category debug row) since there's no longer a single tunable distance — only `drop_duration`/easing stayed tunable.
- **Global tower peak, not per-column height, drives the spawn formula.** Considered computing spawn height from the height specifically under the brick's target columns instead (a more "local" fall), but that would need new per-column height tracking that doesn't exist anywhere in the current data model (`Tower_Stability.topHeight()` only ever tracks one tower-wide scalar). Rejected in favor of reusing `topHeight()` as-is: since stability's overhang/lane-imbalance penalties already discourage lopsided towers, global and local height rarely diverge much in practice, so the simpler approach costs little accuracy.
- **Explicit non-goal: no stability/balance rebalancing in this pass.** `Tower_Stability.settleBlock`/`evaluate` needed zero internal changes (both only ever consumed a caller-supplied `originX` and resolved cell coordinates, never lane/grid-width assumptions directly) — confirming the "must stay a pure function" constraint holds. Stability weights and the target-height curve are untouched even though the placeable footprint narrowed from 3-of-9 to 6-of-14 columns, which will likely need a future tuning pass; see the balance-tuning warning banner in [gameplay.md](./gameplay.md).
- **Bot Manager / Balance Simulator reworked in lockstep.** `chooseBotLane`/`chooseStablestLane` (which iterated `Object.keys(placeableLanes)`) became `chooseBotColumn`/`chooseStablestColumn`, iterating the integer range from `getPlaceableOriginRange(block)` instead — same highest-stability-wins heuristic, just over columns instead of lane names.
